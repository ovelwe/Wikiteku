# Эксплуатация Wikiteku

## Размещение

Production: [wikiteku.vercel.app](https://wikiteku.vercel.app). Исходники: [ovelwe/Wikiteku](https://github.com/ovelwe/Wikiteku).

Vercel-проект `wikiteku`, команда `owelves-projects`, Node 26. Настройки в `vercel.json`: Next.js, webpack, функции во Франкфурте. Neon `wikiteku-db`, план `free_v3`, регион `fra1`; используется существующий pg/Drizzle с транзакциями. Отдельная новая БД `neondb` содержит миграции 0000–0009. Локальные аккаунты, статьи и файлы в production не переносились.

Vercel Marketplace подключает `DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `RESEND_API_KEY`, `RESEND_EMAIL_DOMAIN`. `BETTER_AUTH_SECRET` создан случайно и хранится как Secret, `BETTER_AUTH_URL=https://wikiteku.vercel.app`. Секреты не попадают в Git или артефакты деплоя. Права модераторов по умолчанию отсутствуют.

## Обновление

1. Проверить `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build --webpack`, `pnpm audit` и GitHub Actions.

CI использует официальный `mcr.microsoft.com/playwright:v1.64.1-noble` с готовыми браузерами и PostgreSQL 17 в изолированной service-сети. Версия образа должна совпадать с @playwright/test в lockfile. DB-тесты разрешают только localhost/127.0.0.1 либо hostname postgres при CI=true и только имя БД с префиксом wikiteku_ci. Production URL/секреты в CI не используются.
2. Для изменений схемы заранее сделать резервную копию. Не использовать `db:push` для production.
3. Получить окружение в игнорируемый отдельный файл:

```powershell
npx vercel@65.11.0 env pull artifacts/.env.production.local --environment=production --scope team_VgDUJb6MoLbP8IDoiv9CCdAb --yes
node --env-file=artifacts/.env.production.local node_modules/drizzle-kit/bin.cjs migrate
```

Перед миграцией проверить hostname и имя БД без пароля. Drizzle предпочитает `DATABASE_URL_UNPOOLED`. В этой Windows-сессии `node --env-file=... --run db:migrate` не передал нужное окружение дочерней команде: использовать проверенный прямой запуск выше и после него проверять таблицы и журнал миграций в целевой базе.

Secret-переменные Vercel могут выгружаться как `[SENSITIVE]`. Не загружать эти заглушки обратно в Vercel и не копировать файл вместо локального `.env.local`. Не печатать содержимое файла.

4. Деплой:

```powershell
npx vercel@65.11.0 deploy --prod --yes --scope team_VgDUJb6MoLbP8IDoiv9CCdAb
```

5. Дождаться Ready, открыть главную, каталог и вход. Затем `SMOKE_BASE_URL=https://wikiteku.vercel.app node scripts/check-security.mjs --public` (в PowerShell переменная задаётся через `$env:SMOKE_BASE_URL`). После разрешённого открытия регистрации добавить `--registration-open`: пустой ввод должен отклоняться 400 без создания аккаунта. Локальные тестовые пароли в production не отправлять.

## Почта и регистрация

Бесплатный Resend `wikiteku-mail` подключён к production. Домен `6-7corp.ru` подтверждён 5 ноября. Отправитель: `Wikiteku <noreply@6-7corp.ru>`. Рабочая почта домена продолжает использовать прежние MX; для Resend добавлены TXT `resend._domainkey` и CNAME `rsend`/`send`.

`PUBLIC_REGISTRATION_ENABLED` по умолчанию выключен. Включение требует отдельного разрешения на открытие production-регистрации, корректного ключа и домена. Локальный `ALLOW_LOCAL_REGISTRATION` не открывает production. При включении обязательны письмо и подтверждение email, до подтверждения сессия не выдаётся. Ссылка действует час; после неё пользователь входит обычным способом. При попытке входа без подтверждения отправляется новое письмо в пределах квоты.

5 ноября пользователь явно разрешил открытие. В production установлен `PUBLIC_REGISTRATION_ENABLED=true`, релиз `dpl_E4hcMXYtafNrBVjR6JSdhVMUy27i` Ready и обслуживает основной домен. Форма `/register` и HTTP-сценарий `--public --registration-open` проверены. Пользователь подтвердил получение письма, подтверждение email и успешный вход на реальном адресе; массовая доставляемость по почтовым провайдерам отдельно не проверялась.

Защита: серверная схема имени/логина/email/пароля, удаление клиентских claims `emailVerified`/ролей, honeypot, 5 регистраций/час и 10 входов/минуту на источник в Better Auth; повторная отправка 3/час. Общие атомарные квоты писем в PostgreSQL: 90/сутки UTC на платформу, 3/сутки на адрес. Ошибки отправки тоже расходуют квоту; автоматических бесконечных повторов нет. Почтовые ссылки и ключи не логировать. Это базовая защита; целевой массовый спам может потребовать отдельного challenge/WAF.

Исправление формы 5 ноября: общий `.form-card label` перебивал скрытие honeypot Website. Поле перенесено в контейнер с `hidden` и inline `display: none`, не зависящий от загрузки или специфичности общих стилей. Серверная проверка пустого значения сохранена. Локальная браузерная проверка прошла для RU/EN, Light/Dark и с отключёнными CSS: настоящие поля видны, honeypot скрыт, исключён из доступных textbox и порядка Tab. Типы, Biome, 30 тестов и production build прошли; 3 интеграционных теста без отдельного RUN_DATABASE_TESTS пропущены.

## Наблюдение и квоты

Проверять Vercel Runtime Logs, Usage и Neon Storage/Compute. Главная и каталог выполняют реальные запросы к PostgreSQL, поэтому HTTP 200 этих страниц проверяет и доступность БД. Ошибки 5xx, частые 429 и рост размера БД требуют разбора до смены тарифа. Пул приложения: максимум 5 подключений на экземпляр, подключение до 5 секунд, SQL до 15 секунд, idle 10 секунд.

На 5 ноября 2026 [Vercel Hobby](https://vercel.com/docs/plans/hobby) включает 100 GB Fast Data Transfer, 1 млн вызовов функций, 4 CPU-часа и 360 GB-часов памяти; только личное некоммерческое использование. [Neon Free](https://neon.com/pricing) указывает 1 GB хранения и 100 CU-часов на проект. Это общие условия провайдеров, фактическое потребление смотреть в кабинетах. Платные планы не включались.

[Resend Free](https://resend.com/pricing) включает 3000 писем в месяц и 100 в день; лимит приложения 90/день оставляет небольшой запас. Чужие приложения этого же аккаунта могут расходовать общую почтовую квоту.

Производительность: добавлены частичные индексы публичных страниц/фандомов и индекс автора; повторные чтения фандома/роли/статьи дедуплицируются только в рамках запроса через React.cache. Списки статей выбирают поля карточек, не читают полный Markdown до 100 страниц. Во время проверки три полных HTTP-ответа на маршрут заняли: главная 137–489 ms, вход 115–128 ms, каталог 116–169 ms. Это единичные сетевые измерения из текущей сессии; нагрузочные пределы и полевые LCP/INP не измерялись.

Загрузка ограничена 2 MiB, макет 256 000 байт, тема 12 000 байт; это ниже [лимита Vercel Function 4.5 MB](https://vercel.com/docs/functions/limitations). Медиа хранятся в PostgreSQL как base64 и расходуют больше физического объёма, чем исходные файлы. 50 MiB на фандом не заменяет общий лимит Neon: учитывать индексы, историю и резерв места, не обещать неограниченную бесплатную ёмкость.

## Резервные копии и восстановление

5 ноября создан `artifacts/backups/before-release-20261105.dump` (PostgreSQL custom). `pg_restore --exit-on-error` восстановил его в отдельную локальную `wikiteku_restore_20261105`. Количество строк и MD5 канонического JSON содержимого совпали для 19 таблиц данных, включая аккаунты, статьи, оформление, медиа, переводы и аудит. Из сравнения исключены изменяемые session/rate_limit/verification. Журнал содержал 9 миграций; после восстановления успешно применена 0009 с индексами. База проверки сохранена.

Рабочая локальная `wikiteku` не очищалась. Ранее созданный архив 23 октября сохранён. Каталог `artifacts/` исключён из Git и Vercel; архивы содержат персональные данные и должны храниться отдельно с ограниченным доступом.

Дополнительно проверен сам production Neon PostgreSQL 18.6: `artifacts/backups/neon-before-launch-20261105.dump` включает схемы приложения public/drizzle без владельцев и ACL провайдера. Он восстановлен в отдельный локальный контейнер `wikiteku-neon-restore-18`, база `wikiteku_neon_restore`, порт 127.0.0.1:5433. Восстановлены 22 таблицы public и 10 миграций; на момент снимка аккаунтов/фандомов/статей ещё нет. Для этого сервера нужен pg_dump 18 или новее. Использованы verify-full и доверенный CA-bundle; проверка TLS не отключалась.

При явном dump схем public/drizzle архив содержит CREATE SCHEMA public, а новая PostgreSQL уже имеет public. В проверке использован TOC `artifacts/backups/neon-restore.list` с исключением только создания уже существующих схем; остальные объекты восстановлены с `--exit-on-error`. Перед использованием такого списка обязательно проверить пустоту целевой базы. Не игнорировать произвольные ошибки pg_restore.

Порядок восстановления: остановить запись → сделать актуальный backup повреждённой базы → создать новую пустую базу → восстановить custom dump с остановкой на ошибке → применить последующие миграции → сверить ключевые таблицы, ревизии и журнал → запустить приложение на восстановленной базе и проверить чтение/вход/публикацию → только после проверки переключить production DATABASE_URL и сделать новый деплой. Не восстанавливать поверх действующей базы и не удалять исходную до проверки.

Для отката кода использовать предыдущий проверенный Vercel deployment, совместимый с текущей схемой. Откат кода не откатывает БД; обратные разрушительные миграции автоматически не выполнять. При проблеме регистрации закрыть переключатель и передеплоить.
